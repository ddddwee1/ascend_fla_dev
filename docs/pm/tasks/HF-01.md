# HF-01 回溯核查：A5 FP32 cube matmul 的 HF32 状态继承是否污染过已有真机精度记录

- 波次 / SoC：W0 / a5
- 优先级：P0（缺口 `a5-fp32-cube-matmul-inherits-hf32` 的直接后续）· 时限：16h · 依赖：无
- 需要：A5 真机（D-PM-34）、ascriptor workspace
- 写集：`tmp/HF-01/**`（诊断脚本与证据，不提交）；如果需要给既有单元补 `set_hf32(False)`，
  写集扩大到 `kernels/projects/a5/{kda_fwd_stable,kda_bwd_stable,kda_scan_diag}/**`

  回溯核查做完、把要不要修报给用户决定。

## 这条任务是怎么来的

PK-07 第二轮（PKDA chunk 前向 cube port）真机复现了一个仓库级 P0 缺口：A5 上 FP32 cube
matmul 从未显式设置 HF32 舍入位，kernel 发射不重置这个位，共享卡上会继承前一个租户的设置，
静默把精度降到 HF32——已经用 `set_hf32(True)`/`set_hf32(False)` 做过决定性复现（分别 6/6
与 30/30 次重现对应的输出 hash）。暴露面是 `kda_fwd_stable`、`kda_bwd_stable`、`kda_scan_diag`
三个单元，这些单元现在都挂着"已验证"的真机 FP32 精度数字（见 `docs/matrix/ops.json`）。

用户明确要求回溯核查：这些已有的真机精度记录，是否可能在测量当时就已经被污染过。

## 目标（诊断，不是修复）

对 `kda_fwd_stable`、`kda_bwd_stable`、`kda_scan_diag` 三个单元：

1. 读源码，找到每一处 FP32 cube `matmul` 调用点，确认目前确实没有设置 HF32 位（不要假设，
   PK-07 的发现只核实了 PKDA，这三个单元要分别确认）。
2. 对每个单元，用真机**同一组输入**，分别在 `set_hf32(True)` 和 `set_hf32(False)` 下跑一遍
   现有的真机验收 case（找 `docs/matrix/ops.json` 里记录的那组 case，或者各单元自己的
   `validation.json`），比较两者相对真实参考（CPU FP32 oracle）的误差。
   - 如果两者误差都在原验收预算内、且相差不大：说明这个单元的具体 case 对 HF32 不敏感，
     历史记录大概率没被污染（但仍是运气好，不是设计保证）。
   - 如果 `set_hf32(True)` 下误差明显更大、甚至可能超出原预算：说明这个单元**确实可能
     被污染过**，历史"已验收"的结论需要打问号。
3. 如实记录每个单元的结论，不要互相替代（三个单元可能结论不同）。
4. 检查这三个单元过往真机验收报告（board.json 里对应任务的 `result`/`reports`）有没有
   提到当时卡是否被共享占用——如果找得到当时的 occupancy 记录，交叉核对一下更有说服力，
   找不到就如实说"找不到，无法回溯确认当时卡的状态"。
