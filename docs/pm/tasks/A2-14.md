## 这条任务是怎么来的

A2-03（PR #113，已合入）把 `kda_fused_recurrent`（decode，逐 token 递推，`T<=16`）连同 `kda_fwd_stable`
一起移植到 A2，8 个契约 case（含 `kimi_decode` / `kimi_decode_gqa` 两个用 Kimi-Linear 真实 `H/HV` 的 case）
过了 reference / sim / pipesim 三条流水线，并在 910B3 / CANN 9.0.0 上跑通 aclnn 真机、数字与预算都对，**但
当时 `AGENTS.md` §2 的规则是"A2-11 之前 A2 数字只作观测"**，所以 `contract.json` 里 `board` 这一条 stage
显式标成 `untested`，只作观测记录，不算数。

A2-11（PR #130 → `652dfc0`，2026-09-23）已完成，用户已裁定"满足四项前提的 A2 数字从此可以算数"（`AGENTS.md`
§2）。这条任务把 `kda_fused_recurrent` 这个单元**重新、独立地**在真机上过一遍验证并把 `board` 这条 stage
按新规则落地——不是把 A2-03 的旧数据换个标签，是本任务自己出证据（D-PM-34：所有任务都要真机验证，A2-11
不豁免这一条，它只改变"数字算不算数"，不改变"要不要自己测"）。

顺带补齐 A2-12 留下的一个明确空档。A2-12（KDA 前向 chunk 路径的同类任务）验收原文写的是：

> "decode 不在本任务范围，`kda_fused_recurrent` 的门控跨度另算，若来不及可以只交 chunk 的、把 decode

## 申领人 source_check 核实结果（PM 已读源码核实，不是转述）

申领人在 APPLY 里指出："看板/issue 骨架写 `dtype=fp32`，但 `kda_fused_recurrent` 的实际 ABI 是
q/k/v 与 o 为 BF16、g/beta/h0/final_state 为 FP32"，并提示不要把旧 A5 全 FP32 decode 的预算误套到这个
BF16 输出上，也不要用 host widen/cast 补出不存在的 FP32 入口。

**核实结果：这条是对的。** `kernels/projects/a2/kda_fused_recurrent/contract.json` 现有 `inputs`/`outputs`
字段本身就正确记录了这个混合 dtype ABI（q/k/v: bfloat16，g/beta/initial_state/final_state: float32，
o: bfloat16）；看板 `A2-14.dtype` 字段的 `["fp32"]` 只是任务骨架早期一个粗粒度标签，与契约的真实 per-tensor
dtype 不一致。PM 已把看板字段改成 `["bf16", "fp32"]` 以消除这个不一致（随本次 ASSIGN 一起提交）。

契约现有预算——`o`: `rel_L2 <= 0.005`（`rtol=1e-2, atol=1e-4`，参照 FP32 参考，理由是"floor 是 BF16 舍入，
实测 1.63e-3~1.71e-3，预算取约 3 倍"）；`final_state`: `rel_L2 <= 1e-5`（`rtol=1e-5, atol=1e-6`，FP32
全程）——**本任务沿用这两个数字，不新定**，除非真实形状下的真机重测证明它们不够，那是 RISK 报 PM，不
自行放宽。

关于"公共 `fused_recurrent_kda` 仍绑定 A5 typed kernel"：PM 已读 `ascend_fla/ops/kda/fused_recurrent.py`
核实——`_unit_root()` / `_native_kernel()` 硬编码 `kernels/projects/a5/kda_fused_recurrent*`，`resolve_soc`/
`require_qualified` 只是做 SoC 门控检查，不做路由；`CAPABILITIES["a2"]["qualified"]` 现为 `False` 且
其 `evidence` 字段明写"公共 dispatch 尚未接线，保留未验收总开关"。这与 A2-12 对 `kda_fwd_stable`（chunk
路径）的处理完全对称：A2-12 同样只在独立的 A2 单元层面做验证、填 `CAPABILITIES["a2"]` 的能力表，**没有**
碰 `ops/kda/chunk.py` 的路由逻辑。**本任务照抄这个先例：不做公共入口路由/新 dtype 实现，只资格化现有 A2
单元**，回答申领人自己提出的"是否包含公共路由"的问题——不包含。公共路由接线是否要做、何时做，是后续
独立任务的范围（板上目前没有编号，如果本任务做完后 PM 认为该开会新开，不在这条任务里预支）。

## 范围

1. **真实形状 acc**：Kimi-Linear 真实参数 `H=HV=32, K=V=128`（`models.json` 主形状，`head_group_ratio=1`，
   无 GQA）在 A2 真机上跑 `kda_fused_recurrent`，`T` 至少取 `{1, 4, 8, 16}`（`T_MAX=16`，契约 case
   `t_max` 已覆盖 `T=16` 但 `H=HV=1`，本任务在真实 `H=HV=32` 下补全这几个 `T`），`block_dim` 取契约声明的
   `{1, 2}`。对**独立的** CPU FP32 参考（`kernels/projects/a2/kda_fused_recurrent/reference.py` 的
   `independent_reference`——不要偷懒直接比对 kernel 自己的中间态）报 `o` / `final_state` 相对 L2，
   预算沿用契约现有值（见上）。
   同时报 **torch_npu 组合实现**作为第二 oracle（`AGENTS.md` §6 双 oracle 纪律，两个 oracle 的差异本身
   是信息，不能只报一个）。如果这台 A2 机器缺 `ascend950` 内置算子包、`torch_npu` 组合算子不可用
   （`AGENTS.md` §5 的表），如实记录"本机无法测第二 oracle，原因是缺 XXX 算子"，不要因此跳过不提。
2. **chunk↔decode 状态传递一致性（"chain"）**：`AGENTS.md` §6 的金律——"chunk 与 recurrent 两条路径在数学
   上等价，互为最好的 oracle；prefill/decode 一致性同理"——这次要在 A2 上实测验证，不能假设它从 A5 继承。
   用 A2-03 已经移植好的两个 A2 单元：
   - 用 `kda_fwd_stable`（chunk）跑一段真实形状的 prefix（建议 128 token，对齐 `docs/matrix/gaps.json`
     `decode-call-overhead` 那条踩过的"prefill 64 token 在某些形状下会撞门控"的教训，不要选 64），
     产出 `final_state`；
   - 把这个 `final_state` 作为 `initial_state` 喂给 `kda_fused_recurrent`，逐步单 token 解码若干步
     （建议 ≥5 步），与"整段一次用 `kda_fwd_stable` 算完"的参考比对；
   - **逐 token 报相对 L2，不要只报平均**——`AGENTS.md` §6 明写了这条教训："state 漏传只会坏前几个
     token，平均会掩盖它"。
   - 另外验证契约本身该有的"decode 逐 token 调 T 次并串接 state"与"decode 一次调 T 个 token"在 A2 上
     是否一致（A5 版本这两条逐位相同）——契约 case 目前只有单次调用 `T<=16` 的 case，没有分段调用的
     case，本任务在真实 `H=HV=32` 形状下补这个对照，报数字（逐位相同或给出相对 L2）。
3. **bd / split 网格**：
   - **bd**：真实 `H=HV=32` 形状下确认 `block_dim=1` 与 `block_dim=2` 的输出**逐位相同**——`AGENTS.md`
     §6 的硬判据："核切分不改算式，`bd=1` 与 `bd=4` 的输出应当逐位相同，而且只有 `B*HV` 足够大时才真正
     压到切分逻辑"；`B*HV=32` 满足这个条件。不同就是切分 bug，按 §6.5 的三步流程记账，不是本任务自己
     动手改 kernel。不测 `{1,2}` 以外的 `block_dim`（超出契约声明范围；要扩范围是另一件事，不在本任务
     里顺手做）。
   - **split（GQA head grouping）**：契约已有 `kimi_decode_gqa` case（`H=16, HV=32, block_dim=2`，对应
     `models.json` 的 `long_context` 场景）；本任务补一次同形状、`block_dim=1` 的真机跑法，与
     `block_dim=2` 做上面同样的逐位比对。
   - **splitK 累加链豁免（记录，非实现）**：核实 `kernels/projects/a2/kda_fused_recurrent/kernels/step.py`
     的源码——PM 已用 AST 扫描确认这个 kernel **不含任何 `matmul(...)` 调用**（纯逐行 vector 操作，
     一次一个 state 行），所以 `AGENTS.md` §7"A2 专属·永久禁止"（BF16/FP16 splitK 在 `M<64`）与
     M10-081 的手写 FP32 累加链风险**对这个 kernel 不适用**——不是"跳过了检查"，是"两条规则的前提
     （matmul 调用）在这个 kernel 里都不存在"。`tests/test_a2_accumulate_barriers.py` 本身是对
     `kernels/projects/a2/**` 的全量 AST 扫描（不按单元名单独跳过），这个 kernel 已经天然通过，
     不需要单独改这个测试文件。本任务只需把这条核实结果**写进** `contract.json` 的 `provenance` 或
     一条新 note（连同"怎么核实的"：AST 扫描 `kernels/step.py` 无 `matmul` 调用），供以后的人不用
     重新查一遍。
4. **`ascend_fla/platform.py` 补 decode 能力**：把 `CAPABILITIES["a2"]["supported_block_dim"]` 加上
   `"decode"` 键，值是本任务真机实测的安全 `block_dim` 集合（预期就是契约声明的 `(1, 2)`；如果测出
   更大的安全值也如实写，但不要专门为了扩大范围去试没在契约里声明的 `block_dim`——那是另一件事）。
   decode 路径**没有跨 token 的门控跨度约束**（每步只用当前 token 的 `exp(g)`，契约 `domain.gate_span`
   字段已经写明"no chunk-span limit"），所以不要往 `CAPABILITIES["a2"]["max_gate_span"]` 里塞 decode
   的数字，也不要让 decode 被 chunk 的 `158.0` 上限管到——如果需要标注，加一句注释说明"decode 不受这个
   字段约束"，避免以后有人误读。`CAPABILITIES["a2"]["qualified"]` 不动（A2-12 定的规矩：这个开关只有
   PM 审过才翻，assignee 不自己改）。
5. **`contract.json` 的 `board` stage 落地**：真机重测通过之后，把 `support[]` 里 `stage=="board"` 那一条
   从"pre-A2-11 观测"的措辞改写成"满足 `AGENTS.md` §2 四项前提的真机结论"，并且**逐项点名**这四项前提
   在这个 kernel 上怎么满足的（尤其是"没有手写 FP32 累加链 / splitK"这条，直接引用上面第 3 点的核实
