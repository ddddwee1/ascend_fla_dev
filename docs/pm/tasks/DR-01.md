## 与本仓惯例的偏离（已被用户知情批准，不是 PM 自行放行）

- **不是 ascriptor 单元**：没有 `unit.py` / `contract.json` / `run.py`，`tools/unit_runner.py`
  驱动不了它。AGENTS.md §9 说 `kernels/projects/<soc>/` 下是本仓自建的 ascriptor 单元，
  这个目录不遵循那个协议——目录本身在 README 里显式声明了这一点，不是隐藏起来的。
- **工具链是 PyPTO-Pro**（`pypto` 0.2.1），不是 ascriptor：九个 kernel 用 `@pl.jit` /
  `@pl.vector_function` 直接写。这是"要不要接受 ascriptor 之外的工具链"这个仓库定位问题的
  第一个实例——用户这次的决定**只覆盖这一个 PR**，不代表"以后 PyPTO-Pro 单元默认可以合入"，
  再来一个要再问。
- **纯加法、零耦合**：这个目录自己不被仓内任何其它文件 import，新增文件全部在这一个新目录下，
  不改 `pyproject.toml`、不碰 `.github/`、无新依赖、无二进制文件、无网络/凭据/eval/exec 代码
  （PM 已扫描确认）。即使以后要搬到 `docs/research/` 或移除，都不会破坏其它代码。
- **算法族是 `delta_rule`（DeltaNet，标量门控），不是 GDN-2**（GDN-2 是逐通道门控）——
  这是 README 状态表里"尚未排任务"的那个算子族，与 `docs/matrix/ops.json` 里已有的
  ascriptor 单元 `a5.delta_rule_fwd` / `a5.delta_rule_bwd`（已有 `board_*` 验证记录，
  但 `wiring/binding/accuracy_vs_oracle/perf_vs_baseline` 全部 `not-started`）是**同一个
  算子族、不同的实现路径**，彼此不冲突、不重复——那两个 ascriptor 单元至今没有被接成可调用的
  op（这条任务也不接），只是同一算子族里并存的两套素材。
