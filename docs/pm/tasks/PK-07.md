# PK-07 PKDA chunk 前向：性能优化（先 profile 再动手，一次一个改动）

- 波次 / SoC：W0（同 PK-02/PK-04）/ a5
- 优先级：P2 · 时限：16h · 依赖：`PK-04`（已 done，PKDA chunk 前向的 A5 真机验收）
- 需要：A5 真机（D-PM-34）、ascriptor workspace
- 写集：`kernels/projects/a5/pkda_chunk_fwd/**`、`ascend_fla/ops/pkda_chunk_fwd.py`、
  `tests/test_pkda_chunk_fwd.py`、`docs/research/pkda_chunk_fwd_gate_range.md`

## 这条任务是怎么来的

PK-04 交付的是一个**正确的、已过真机验收**的 FP32 实现，性能优化明确不在它的范围内（同类任务
一贯纪律：先把正确性和真机验收做完，优化是下一个任务）。用户直接要求开这条优化任务。

**当前已知的基线数字**（PK-04，A5 真机，三轮同卡三明治，`docs/pm/board.json` PK-04.result.numbers，
`kernels/projects/a5/pkda_chunk_fwd/evidence/perf-t{1024,4096}.json`）：

| 形状 B1/H8/K=V=128 | 对比对象 | 比值 |
|---|---|---|
| T=1024 | pinned FLA naive（torch_npu eager） | PKDA 候选 ≈0.077（**快约 13 倍**） |
| T=4096 | 同上 | PKDA 候选 ≈0.038（**快约 26 倍**） |

- `block_dim=4`，仅 FP32（BF16 被这个单元显式拒绝，不在本任务改动范围——BF16 版本是独立任务
  BF-04，不要在这里混着改）。
- 这个基线是"pinned FLA naive 在 torch_npu 上 eager 跑"，**不是**调优过的参照，所以"已经比它快
  13-26 倍"不代表没有继续优化的空间——这条基线从一开始就没打算当作性能天花板，只是正确性/
  速度量级的参照。**本任务不预设瓶颈在哪**，第一步仍然是先 profile 当前实现本身的 stage 级
  耗时，不是和这个基线比。

## 步骤

1. **先 profile 已验收版本本身，不要先猜瓶颈**（AGENTS.md §6 铁律一）。真机上跑
   `docs/matrix/models.json` 里的真实形状（不是只测 T=1024/4096 这两个玩具长度——那两个是
   PK-04 的契约验收形状，不代表 Kimi-Linear-48B-A3B 的真实调用形状），拆 stage 级（gate/
   WY/triangular-inverse/intra/recurrent，参照 `kda_fwd_stable` 的五段结构）与调用级计时，
   device 侧耗时与 host 侧开销拆开报（§6 铁律一）。同时拿 CPU golden 核对正确性没退步。
2. **一次只改一处，逐次对照**（AGENTS.md §6 铁律二：一个算子名、一个进程、一份 build）。
   不预设第一轮方向——profile 数据出来之前不要先决定"肯定是哪一段慢"。
3. 每改一处，重跑：
   - 契约 case 在 `block_dim ∈ {1, 2, 4}`（这个单元已知支持到 4）上过，**不同 `bd` 间逐位
     相同**——这是不需要参考的硬判据（核切分不改算式，不同就是切分 bug，不是精度问题）。
   - 静态检查、sim/pipesim 诊断、真机正确性全部重新跑一遍——源码变了，证据要跟着重新产生，
     不能复用 PK-04 时的旧记录。
4. **性能验收看真实形状是否稳定变快**：同卡同步三明治（baseline-candidate-baseline，
   warmup=10、repeat≥50，三轮），对照本任务自己 step 1 产出的 profile 基线（不是 PK-04 的
   T1024/T4096 玩具数字）。**只留下稳定变快的改动**；试过但没达标的，把对照数据留下来
   （负结果也是证据，不要悄悄删掉）。

## 验收线（2026-10-27 用户直接给出，适用于本任务及之后所有性能优化任务）

- [ ] **开始优化前**：升级到最新 PyPTO-Pro 框架，并安装官方插件
      [`pypto-pro-op-orchestrator`](https://gitcode.com/cann/pypto-gym/tree/master/cannbot-skills/plugins-official/pypto-pro-op-orchestrator)
      （`cann/pypto-gym` 仓库，不是 `cann/cannbot` 的社区版）。见 AGENTS.md §6"性能优化
      任务的验收线"。
- [ ] **量化停止线**：每个被改动的 kernel，最终版本要达到计算 bound 或搬运 bound——
      对应资源（cube/vector 算术管线，或 MTE2/MTE3 搬运管线）的 `PipeUtilization` 实测
      ≥85%。没打到就要么继续优化，要么如实写清楚"卡在哪条 pipe、利用率多少、离 85%
      差多远"，不能用"比基线快很多"替代这条量化判据。

## 验收

- [ ] 已验收版本在真实形状（`docs/matrix/models.json`）上的 stage 级 + 调用级 + device/host
      拆分基线 profile 数字（原始样本，不只是均值）。
- [ ] 每个候选改动单独对照：改前改后的 profile 数字、正确性数字都在，不是只报最终版本。
- [ ] 契约 case 在 `bd∈{1,2,4}` 上全过，彼此输出逐位相同。
- [ ] 精度判据不放松：FP32 判定、1e-4 预算不变，不因为要显性能而调松。
- [ ] 最终性能数字：真实形状上相对本任务自己的 step-1 基线稳定变快，三轮同卡同步三明治。
- [ ] 失败的候选改动留有对照记录，不隐藏负结果。
- [ ] `git diff --stat` 对 `reserved_paths`（GDN-2，见看板）为空；公开 API 签名不变；
      不碰 BF16 版本（`kernels/projects/a5/pkda_chunk_fwd_bf16/**`，那是 BF-04 的写集）。
- [ ] 每份真机数字带 SoC + CANN（带时间戳）+ opp 算子包 + 原始日志行（PROTOCOL §3.7）。

## 已知陷阱

- **不要把这条做成"顺便修正确性"**——数学已经在 PK-02/PK-04 验收过，这里只优化实现，
  改动前后的正确性判据必须逐位/按预算不变，变了就是引入了新 bug，不是优化。
- AGENTS.md §6 铁律三：缓存键不能比缓存贵——如果优化路径引入任何形式的运行时缓存/查表，
  确认开销是 O(1) 级别。
- `block_dim` 对比必须一份 build 一个进程（§6 铁律二），不要在同一进程里换 `bd` 复用缓存
  （KDA 那条"profile 之前不要相信推断"的教训踩过两次，别重蹈）。
- 这个单元只接受 FP32，本任务不新增 BF16 支持（那是 BF-04 的范围）。
- 复用 PK-04 报告里的 T1024/T4096 数字做"量级参照"没问题，但**优化对照用本任务自己 step 1
  的真实形状 profile 数字**，不要拿 PK-04 的玩具形状数字当优化基线。
