## 这条任务是怎么来的

BF-09（2026-09-21/22，PR #128，已 done）给 KDA raw flags 训练前处理反向 kernel
做过一轮性能优化：T4096 完整训练步从合入版 428.86ms 降到 223.06ms（降 48%），但
对比基准是"旧 host 图"和"Torch NPU"的*墙钟*耗时比值，不是 `PipeUtilization`——
AGENTS.md §6 2026-10-27 定下的 85% 验收线**覆盖所有历史记录，不只新任务**：
"一个 kernel 现在有没有被量过 pipe 利用率、达没达到 85%，看 ops.json 对应条目有没有
记这项——没记的，按'未验证'处理"。`docs/matrix/ops.json` 里目前没有 `kda_prep` 的
`aic_mac_ratio`/`aiv_vec_ratio`/`mte2`/`mte3` 记录。

BF-09 自己的收尾已经给出一个有用的起点：**profiler 条件下界 164.428501ms**（gate
第一阶段），即消去其它全部 kernel 最多还能再快 1.329×——这意味着 gate 第一阶段
本身占了训练步绝大部分耗时，是本任务 profile 的第一个落点，不用从零开始找瓶颈。

## 目标

1. **先用真机 profile 把 `kda_prep` 的每个 kernel 的 `PipeUtilization` 测出来**
   （真实形状，`docs/matrix/models.json`，不是契约玩具形状）。重点先看 gate 第一阶段
   （BF-09 指认的耗时大头）。
2. **按 85% 线判定**：每个 kernel 是计算 bound（`aic_mac_ratio`/`aiv_vec_ratio`）还是
   搬运 bound（`mte2`/`mte3` 占比），有没有到 85%。没到的，定位到具体瓶颈（不是症状
   规律，§6.5），记录差多少。
3. **FP32 cube matmul 检查 HF32 设置**——如果 `kda_prep` 有 FP32 操作数的 cube matmul，
   按 `a5-fp32-cube-matmul-inherits-hf32`（P0）的方法核实有没有暴露（真机 A/B，不是
   假设）。
4. **一次只改一处**：如果找到可以安全改的瓶颈，同 KDA-P1/GDN-P1/DR-P1 的验证标准——
   CCE 发射 diff 精确、双 oracle 精度不变（FP32 判定）、跨 `bd` 逐位相同、真机同卡
   同步三明治测真实提升。**冻结预算文件（`backward_budgets.json`）字节不能变**——
   这是 BF-09 定下的硬约束，继续遵守，不是本任务可以重新协商的。
5. **方法论提醒**：今天（2026-10-30）KDA-P1、GDN-P1、DR-P1 三个任务独立发现同一个
   问题——`aiv_vec_ratio`/`aic_mac_ratio` 高不等于已经到位的充分证据（DR-P1 甚至测到
   一个逐位相同但更慢 1.13~1.69x 的配置反而"过线"）。如果本任务也遇到类似现象（改了
   之后占用率升但实测变慢，或占用率不足但已经是最优配置），如实记录，不要被占用率
   数字牵着走——报真机耗时，占用率只是辅助诊断信号。
